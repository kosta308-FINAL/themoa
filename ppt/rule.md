# PPT 작업 규칙

## 왜 파일을 나눴나

원래 `index.html` 하나에 슬라이드 전체가 다 들어있어서, 팀원끼리 다른 슬라이드를 고쳐도
같은 파일을 건드리게 되어 git 충돌이 자주 났음. 그래서 슬라이드별로 파일을 분리함.

```
ppt/
  index.html          슬라이드 목록 + 뼈대만 (거의 안 건드림)
  common.css           공통 레이아웃(덱/네비/전환 애니메이션)
  common.js             공통 엔진(다음/이전, 스텝 애니메이션, 화면 맞춤)
  assets/               이미지
  slides/
    intro.js             오프닝 슬라이드
    key-features.js      핵심 기능 소개 (소비가이드/고정지출/전체 소비내역)
    llm-architecture.js  LLM 활용 구조
    team-intro.js        팀 소개
    ...                  담당 슬라이드 하나당 파일 하나
```

- **파일 이름은 번호가 아니라 내용으로 지을 것 (`slide90.js`처럼 X)**: 실제 발표
  순서는 아래 "새 슬라이드 추가하기"에 나오듯 `index.html`의 `<script>` 태그
  나열 순서로 정해지고, 이 순서는 팀원들이 작업하면서 계속 바뀜. 파일명에
  번호를 붙이면 나중에 순서가 바뀌었을 때 파일명과 실제 위치가 안 맞아
  헷갈리게 됨. 그러니 파일명은 `key-features.js`, `llm-architecture.js`처럼
  그 슬라이드가 뭘 보여주는지로 짓기.
- **슬라이드별로 나눈 이유**: 각자 담당 슬라이드 파일만 고치면 다른 사람 작업과
  충돌하지 않음.
- **common.css / common.js를 따로 둔 이유**: 3개 슬라이드가 전부 같이 쓰는 엔진이라
  각 슬라이드 파일에 복붙하면 나중에 네비게이션 하나 고칠 때 파일을 다 고쳐야 함.
  대신 이 두 파일은 팀원이 거의 안 건드리는 파일이라 충돌 위험이 적음.
- **`fetch()` 안 쓰고 `<script src>`로 불러오는 이유**: `fetch()`는 브라우저가
  `file://`로 연 로컬 파일은 무조건 막아서 서버 없이는 안 열림. `<script src>` /
  `<link href>`는 그냥 리소스 로드라서 `index.html` 더블클릭만으로도 항상 동작함.
  **그래서 슬라이드 파일 로딩 방식은 절대 `fetch`/`XMLHttpRequest`로 바꾸지 말 것.**

## 어떻게 작업하면 되는지

### 1. 실행 방법
`index.html`을 그냥 더블클릭해서 열면 됨. 서버 필요 없음.

### 2. 내 슬라이드만 따로 확인하기
전체를 다 클릭해서 넘길 필요 없이, 주소 끝에 `#N`을 붙이면 그 슬라이드로 바로 이동함.
여기서 `N`은 파일명이나 파일 안의 id가 아니라 **`index.html`에 나열된 순서(몇 번째
`<script>` 태그인지)**임. 내 슬라이드가 지금 3번째 자리에 있으면:

```
index.html#3
```

이렇게 열거나(또는 열어놓은 상태에서 주소창에 `#3` 추가 후 새로고침), 이미 열려있는
탭이면 주소창에 `#3` 입력만 해도 바로 그 슬라이드로 넘어감. 다른 슬라이드는 화면
밖으로 밀려나 있어서 사실상 내 슬라이드만 보면서 작업 가능함. 단, 순서가 바뀌면
이 번호도 같이 바뀌니 매번 몇 번째인지 `index.html`에서 확인할 것.

클릭 애니메이션(프래그먼트)이 있는 슬라이드를 전부 펼쳐진 상태로 한 번에 보고 싶으면
`?all`을 붙임: `index.html?all#3`

### 3. 내 슬라이드 고치기
내 담당 슬라이드 파일(`slides/파일이름.js`) 하나만 열어서 수정. 파일 안에 style과
마크업이 다 들어있음.

```js
document.head.insertAdjacentHTML('beforeend', `
<style>
#s-키워드 .뭔가 { ... }   // 반드시 자기 슬라이드만의 고유 id로 시작해서 다른 슬라이드와 안 겹치게
</style>
`);

document.getElementById('deck').insertAdjacentHTML('beforeend', `
<section class="slide" id="s-키워드">
  ...마크업...
</section>
`);
```

- CSS 선택자는 항상 `#s-키워드 .클래스`처럼 **자기 슬라이드만의 고유 id로 시작**할
  것. id는 파일명처럼 내용을 알아볼 수 있는 이름이면 됨(예: `#s-key-features`).
  다른 슬라이드 파일과 클래스 이름이 겹쳐도 이렇게 스코프를 걸어두면 서로 안 건드림.
- 백틱( ` ) 문자열 안에 코드가 들어있으니, 마크업 안에서 백틱이나 `${ }`는 쓰지 말 것
  (템플릿 리터럴이 깨짐).

### 4. 새 슬라이드 추가하기 / 순서 바꾸기
1. `slides/내용을-설명하는-이름.js` 새로 만들고, 위 형식대로 나만의 id 스코프로
   style + 마크업 작성.
2. `index.html`에서 이 슬라이드가 발표 중 나와야 할 자리에 `<script>` 한 줄만
   추가(꼭 끝일 필요 없음 — 원하는 순서대로 아무 위치에나 넣으면 됨):
   ```html
   <script src="slides/slide3.js"></script>
   <script src="slides/내용을-설명하는-이름.js"></script>
   <script src="slides/key-features.js"></script>
   ...
   <script src="common.js"></script>
   ```
   **실제 발표 순서 = 이 `<script>` 태그들이 나열된 순서.** 파일명이나 파일
   안의 id 순서가 아니라 오직 `index.html`에 적힌 순서로 결정됨.
   `common.js`는 항상 제일 마지막이어야 함 — 모든 슬라이드가 삽입된 다음에
   엔진이 슬라이드 개수를 세기 때문.
3. 순서를 바꾸고 싶으면 `index.html`에서 `<script>` 줄 순서만 바꾸면 됨. 각
   슬라이드 파일 자체는 안 건드려도 됨.

### 5. 공통 부분(common.css / common.js / index.html) 고치기
전체 네비게이션, 전환 애니메이션, 레이아웃처럼 슬라이드 전체에 영향 가는 걸 고칠 때만
수정. 다른 팀원 작업과 겹치기 쉬운 파일이니 고치기 전에 팀에 얘기하고 최신 상태로
pull 받은 뒤 작업할 것.

### 6. 자주 하는 실수
- `slides/*.js` 파일을 브라우저로 직접 열면 안 됨 — 이건 `index.html`이 조립해서
  써야 하는 조각 파일이라 단독으로 열면 스타일도 없고 이미지 경로도 깨짐.
  항상 `index.html`을 열어서 확인할 것.
- 자기 슬라이드 CSS를 자기만의 id 없이 클래스명만 쓰면 다른 슬라이드에도 스타일이
  새어나감.
- 파일명을 `slide90.js`처럼 번호로 짓지 말 것 — 순서는 `index.html`이 정하는
  거라 번호가 실제 위치와 금방 안 맞게 됨. 내용을 설명하는 이름으로 지을 것.

### 7. 폰트 규칙
**폰트는 항상 기본값(Pretendard)을 그대로 쓸 것. `font-family`를 따로 지정하지 말 것.**

이유: 슬라이드는 1920×1080 캔버스를 만들어놓고 `common.js`의 `fit()`이 브라우저 창
크기에 맞춰 `transform: scale()`로 통째로 축소/확대해서 보여주는 구조임. 이 축소
과정에서 작게 쓴 글자, 특히 `Courier New` 같은 모노스페이스 폰트는 지글거리는
노이즈처럼 번져 보임(실제로 슬라이드91에서 컬렉션명 태그에 `Courier New 14px`을
썼다가 화면 배율에 따라 뭉개져 보이는 문제가 있었음). Pretendard는 이 정도로
뭉개지지 않으니 특별한 이유 없이는 폰트를 바꾸지 말 것.

- 작은 글자(16px 미만)를 어두운 배경 위에 밝은 색으로 쓰는 것도 배율에 따라
  번져 보이기 쉬우니, 작게 써야 하면 최소 16px 이상 + 폰트는 그대로 유지.
- 코드/DB명처럼 "고정폭 느낌"을 내고 싶어도 `monospace`류 대신 Pretendard +
  `font-weight:700` 정도로 강조하는 걸 권장.

### 8. 텍스트 줄바꿈
설명 문구가 카드 폭보다 길어서 두 줄이 될 때, 브라우저가 알아서 줄바꿈하게
내버려두면 단어 중간(예: "섞이지"가 "섞" / "이지 않습니다"로 끊김)에서 잘려서
읽기 불편함. **문장이 두 줄 이상 될 것 같으면 자동 줄바꿈에 맡기지 말고, 뜻이
끊기지 않는 지점에 직접 `<br>`을 넣을 것.**

```
<!-- 나쁨: 그냥 길게 써서 브라우저가 임의로 끊게 둠 -->
<div class="bdesc">컬렉션이 분리돼 있어 정책 임베딩이 금융상품 검색에 노이즈로 섞이지 않습니다.</div>

<!-- 좋음: 의미 단위로 직접 끊음 -->
<div class="bdesc">컬렉션이 분리돼 있어 정책 임베딩이 금융상품 검색에<br>노이즈로 섞이지 않습니다.</div>
```

`<br>` 넣은 다음엔 반드시 `index.html`을 열어서(또는 헤드리스 스크린샷으로)
실제로 어디서 끊기는지 눈으로 확인할 것 — 카드 폭이 슬라이드마다 다르므로
같은 문장도 카드 폭에 따라 적절한 끊는 위치가 달라짐.

### 9. 슬라이드 순서 구성

`index.html`의 `<script>` 목록은 발표 흐름을 6개 구간으로 나눠 `<!-- N. 설명 -->`
주석으로 구분해뒀다. 새 슬라이드를 추가할 때는 파일을 새로 만드는 것보다 먼저
**이 6구간 중 어디에 속하는 내용인지부터 정하고, 그 주석 블록 안에 한 줄을
끼워 넣는 것**부터 시작한다.

```
<!-- 1. 우리가 만든 것 -->       slide1(표지) · slide93(팀 소개) · intro(인트로 영상)
<!-- 2. 왜 만들었는지 배경 -->    slide2(문제정의)
<!-- 3. 타겟 사용자 -->          about(서비스 소개·타겟)
<!-- 4. 핵심 기능 -->            key-features · slide22~25(정책) · savings-fixedexpense-link
<!-- 5. 어떻게 만들었는지 -->     slide3(설계 흐름도·계획 과정) · slide30~32(기술스택·협업) ·
                                slide92(멀티에이전트) · rag-engineering · llm-coaching-cards ·
                                dev-workflow
<!-- 6. 트러블슈팅 / 마무리 -->   troubleshooting · closing-thoughts
```

- **구간 판단 기준**
  - 서비스가 뭘 하는지, 사용자가 뭘 보는지(기능·화면) → **4. 핵심 기능**
  - 그 기능을 어떤 기술로 어떻게 구현했는지(아키텍처·엔지니어링·트러블슈팅 전 단계) → **5. 어떻게 만들었는지**
  - 개발 도중 겪은 문제와 해결 과정 → **6. 트러블슈팅 / 마무리**
  - 애매하면(예: 기능 소개인지 기술 설명인지) 발표 순서상 청중이 "이게 뭔지"를
    먼저 알아야 하는지("4"), "어떻게 그렇게 했는지" 궁금해질 시점인지("5")로 판단.
- **구간 내부 순서**도 의미가 있다. 예를 들어 "4. 핵심 기능"은 소비관리 →
  정책 추천 → 금융상품 연동 순으로, "5. 어떻게 만들었는지"는 계획 과정(slide3) →
  기술스택 → 아키텍처 → 엔지니어링 상세(RAG·코칭) → 개발 프로세스 순으로 점점
  구체화된다. 새 슬라이드는 같은 구간 안에서도 이 흐름에 맞는 위치에 끼워 넣을 것.
- **구간(대분류) 자체를 새로 추가하거나 순서를 바꾸는 것**은 전체 발표 흐름에
  영향을 주므로, 5번 규칙(공통 부분 고치기)과 마찬가지로 팀에 먼저 얘기하고
  최신 상태로 pull 받은 뒤 작업할 것.
- 슬라이드 순서가 바뀌면 `index.html#N`의 `N`(몇 번째 `<script>`가 아니라
  실제로는 몇 번째 `.slide` 섹션인지)도 같이 바뀌니, 2번 항목처럼 내 슬라이드만
  확인할 때는 그때그때 `index.html`에서 순서를 다시 셀 것.
